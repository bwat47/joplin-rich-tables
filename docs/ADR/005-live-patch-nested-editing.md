# ADR-005: Live-Patch Nested Editing vs In-Memory Table Model

## Status

Accepted

## Context

The nested cell editor is a cell-local CodeMirror instance. It displays logical cell text while the main editor remains the authoritative Markdown document.

One alternative is an in-memory table/session model:

1. Parse the Markdown table into a shared model.
2. Edit active cell content in the nested editor without patching the root document on every change.
3. Commit the model back to Markdown on blur, navigation, or explicit save.

That model keeps table formatting concerns, such as full column-width padding, separate from cell content. It would make it easier to distinguish structural table padding from user-authored leading or trailing whitespace.

The current architecture live-patches the main editor instead:

1. The nested editor opens from the active cell's editable root range.
2. Local edits are sanitized and written back to that root range.
3. The main editor selection is mirrored to the active cell's root document positions.
4. Root changes re-resolve the logical active cell and rebase the nested editor.

This was chosen because Joplin formatting commands operate on the main editor selection and document. As a plugin, rich tables cannot assume it can intercept or replace all of those commands. Keeping the main editor selection live inside the active cell allows native formatting actions to operate on real Markdown text.

## Decision

Keep the live-patch nested editing architecture as the primary editing model.

The main editor remains the source of truth during active cell editing. The nested editor is a focused cell-local view that translates text and selection between:

- local cell coordinates used by the nested editor
- root document coordinates used by Joplin and the main CodeMirror editor

An in-memory table model may still be used for structural table operations and serialization, but it must not replace the live root document as the active editing target unless Joplin formatting command integration is redesigned.

## Consequences

**Positive:**

- Joplin's native formatting commands can continue to work against the real root selection.
- Main-editor history and document state stay authoritative during editing.
- External root-document changes can be observed and rebased into the active nested editor.
- The architecture matches the existing selection sync and command compatibility assumptions.

**Negative:**

- The active cell's editable range must be precise because it defines both what the nested editor sees and what it replaces.
- Source whitespace near table delimiters is hard to classify when canonical formatting adds padding.
- Full column-width alignment padding is more complex than minimal single-space padding.
- Range computation, selection mapping, guard policy, and nested-editor sync remain tightly coupled.

## Implications for Full Alignment Padding

Full alignment padding should not be implemented as a detached in-memory editing session just to simplify serialization.

If full padding is added, the range model must explicitly distinguish:

- raw cell bounds between delimiters
- semantic content bounds
- editable bounds owned by the nested editor
- structural padding generated by canonical table formatting

Hide or replace decorations may be useful for presentation, but they cannot define edit semantics. The source ranges must decide which text enters the nested editor, which root range is replaced, and where mirrored selections land.

## Alternatives Considered

1. **One-way commit through an in-memory table model**: Rejected for the primary editing path.

    This would cleanly separate cell content from serialized table padding, but it weakens compatibility with Joplin formatting commands. Commands that mutate the root editor would need interception, duplication, or a close-and-reopen reconciliation flow.

2. **Close nested editor on external formatting commands**: Rejected for the primary UX.

    This is simpler to reconcile, but it breaks the expectation that native formatting actions work while the cell remains active.

3. **Use decorations to hide structural padding while editing**: Deferred as a presentation tactic.

    Decorations can hide or replace visual padding, but the root document still contains that padding. They do not solve editable range ownership, selection mapping, or transaction guard behavior.
